# Payment Cascading System — Design

## 1. Контекст и зачем

Тестовое задание на этап собеседования (24 часа на всё: архитектура + реализация + README),
язык — Python. Оценивать будут код, архитектуру, покрытие корнер-кейсов и README, затем будет
созвон с CTO с разбором решения. Цель документа — зафиксировать архитектуру до начала кода,
чтобы за 24 часа не переделывать решения на лету.

Система — платёжный гейтвей с каскадированием: пользователь создаёт платёж (депозит/вывод),
гейтвей выбирает провайдера, пробует провести платёж; при отказе — пробует следующего
провайдера по правилам роутинга. Ключевая сложность, которую явно обозначил заказчик: отказ
провайдера не всегда означает отказ по факту (таймаут/5xx при реально прошедшей транзакции), и
это нужно не прозевать, чтобы не задвоить платёж при каскадировании.

## 2. Goals / Non-goals / Anti-goals

**Goals**
- API: создание платежа (deposit/withdraw), получение статуса, приём вебхуков от провайдеров,
  отправка вебхука мерчанту по финализации.
- Роутинг: ручной приоритет провайдера, если выставлен — закон; если не выставлен — адаптивный
  роутинг по истории успешности, с фильтрацией по направлению/типу карты/сумме.
- Каскадирование: при подтверждённом retryable-отказе — следующий провайдер по порядку; при
  финальном отказе (fraud, insufficient funds и т.п.) — не каскадировать.
- Разрешение неопределённости: таймаут/5xx не считается финальным отказом — система уточняет
  реальный исход (status-check или ожидание вебхука с дедлайном) до решения каскадировать.
- Детект конфликта "задвоения": если после каскада на провайдера B приходит поздний вебхук от
  провайдера A, говорящий, что A тоже прошёл успешно — это помечается как conflict, не
  затирается молча.
- Идемпotentность создания платежа (Idempotency-Key) и обработки вебхуков.
- 3 тестовых провайдера-мока с разным поведением, управляемым сценарием — для демонстрации
  каждого корнер-кейса на созвоне.
- README с архитектурой, инструкцией запуска и явным списком ограничений/что было бы иначе
  при большем времени.

**Non-goals** (осознанно не делаем, из-за скоупа/времени)
- Мультитенантность/мерчанты — один логический мерчант.
- Реальные провайдеры — только моки.
- UI — чистый backend API.
- Внешний брокер задач (Celery/Kafka) — внутрипроцессные asyncio-таски поверх состояния в БД;
  в README отдельно отмечается как первое, что заменил бы в продакшене.
- Авторизация — нет (если потребуется на созвоне, обозначается как известный пробел).

**Anti-goals** (провал даже при формальной работоспособности)
- Молчаливое задвоение платежа/выплаты без детекта.
- Каскадирование на отказ, который гарантированно повторится у любого провайдера.
- Потеря истории попыток — по каждому платежу должен быть полный аудит попыток.

## 3. Доменная модель и флоу

**Сущности**
- `Payment`: id, direction(deposit|withdraw), amount, currency, card_bin/card_type, status
  (pending|processing|succeeded|failed|conflict), idempotency_key, callback_url, timestamps.
- `ProviderAttempt`: payment_id, provider_id, status(pending|succeeded|declined_final|
  declined_retryable|ambiguous|timed_out), decline_code, requested_at, resolved_at.
- `Provider`: id, name, priority (nullable → adaptive), supported_directions, supported
  card types, min/max amount, enabled.
- `ProviderStats`: (provider_id, direction, card_type_bucket) → success_count, failure_count —
  основа адаптивного роутинга.
- `ReconciliationFlag`: payment_id, причина конфликта, связанные attempt_id'ы, resolved_at
  (ручной разбор).

**Флоу**
1. `POST /payments` (+ `Idempotency-Key`) → валидация → `Payment(pending)` → асинхронный запуск
   обработки → ответ `202` с `payment_id`.
2. Routing engine отбирает провайдеров: фильтр по direction/card_type/amount/enabled → сортировка
   по manual priority, если задан хоть у одного; иначе по adaptive score.
3. Для каждого провайдера по порядку:
   - создать `ProviderAttempt(pending)`, вызвать адаптер;
   - немедленный финальный результат (success / final decline) → завершить попытку, обновить
     `ProviderStats`;
   - неопределённый результат (timeout/5xx/pending-webhook) → `ambiguous`, запускается
     reconciliation: polling status-check (если есть у провайдера) либо ожидание вебхука, с
     дедлайном;
   - по дедлайну без ответа → для целей каскада считать retryable-failure и идти дальше, но
     попытка остаётся в истории как `timed_out`, а не перезатирается;
   - success → финализировать `Payment(succeeded)`, остановить каскад;
   - final decline → следующий провайдер.
4. Все провайдеры исчерпаны → `Payment(failed)`, агрегированные причины отказа.
5. Финализация → вебхук мерчанту (подписанный, с ретраями при недоставке).
6. Позднее разрешение неопределённой попытки (после того как каскад уже решил исход иначе):
   - совпадает с уже зафиксированным исходом → идемпотентный no-op;
   - конфликтует (например, обе попытки "success") → `Payment.status = conflict` +
     `ReconciliationFlag`, обе попытки остаются видимы, автоматического разрешения нет (это
     бизнес-решение, вне скоупа 24ч — явно прописано в README).

## 4. Принятые решения (мои, с обоснованием)

- **Стек**: FastAPI + Pydantic v2, async/await — провайдеры I/O-bound, нужна конкурентная
  обработка попыток; FastAPI даёт бесплатную OpenAPI-документацию, удобно для ревью кода.
- **БД**: PostgreSQL через `docker-compose` + SQLAlchemy 2.0 (async) + Alembic — ближе к
  реальному продакшену, чем SQLite, при этом поднимается одной командой.
- **Фон. обработка**: asyncio-таски, состояние — в БД (не in-memory), без внешнего брокера.
  Явный компромисс ради срока; в README — что в продакшене это Celery/RQ + Redis ради
  надёжности при падении процесса.
- **Нормализация ответа провайдера**: у реальных платёжных провайдеров нет единой конвенции —
  один шлёт отказ HTTP-кодом (4xx/5xx), другой всегда отвечает `200` и кладёт код ошибки в тело
  ответа. Это разбирает исключительно сам адаптер провайдера: наружу он отдаёт только
  нормализованный `AttemptOutcome` (success / declined_final / declined_retryable / ambiguous +
  decline_code). Остальная система (роутинг, каскад, reconciliation) никогда не смотрит на HTTP
  статус напрямую — только на этот нормализованный результат. Это специально заложено и в моках
  ниже, чтобы корнер-кейс был реально покрыт тестами, а не предполагался.
- **Тестовые провайдеры** (протокол `ProviderAdapter`, 3 реализации, каждая со своей конвенцией
  ответа):
  - `provider_fast_sync` — отвечает сразу, отказ сигналится HTTP-кодом (напр. 402/403);
    настраиваемая вероятность success/decline, среди отказов — и финальные (insufficient_funds,
    fraud_suspected), и retryable (processing_error);
  - `provider_webhook_async` — сразу отвечает `200` с телом вида
    `{"status": "declined", "code": "..."}` (отказ не отличить от успеха по HTTP-коду, только по
    телу); реальный исход при этом приходит позже вебхуком после имитации задержки;
  - `provider_flaky` — непредсказуемо смешивает обе конвенции и добавляет настоящие
    таймауты/5xx, имеет status-check эндпоинт для reconciliation.
  Поведение каждого управляется полем `scenario` в запросе — чтобы на созвоне детерминированно
  воспроизвести любой корнер-кейс.
- **Adaptive score**: сглаженная по Лапласу успешность `(successes + 1) / (attempts + 2)` в
  разрезе (provider, direction, card_type) — простая, объяснимая метрика, не даёт одной первой
  попытке решать рейтинг провайдера.
- **Классификация decline_code**: статическая карта у каждого адаптера → {final, retryable,
  ambiguous}. Это и есть механизм, не дающий каскадировать платёж, который провалится везде
  (insufficient funds), при каскадировании только на инфраструктурных отказах.
- **Idempotency-Key**: обязателен на `POST /payments`; повтор того же key+payload в окне —
  возвращает исходный результат, не создаёт дубликат платежа.
- **Лимит каскада**: safety cap по умолчанию = число подходящих провайдеров, настраиваемый.
- **Дедлайн reconciliation**: конфигурируемый таймаут (демо-масштаб, например 10с) до перехода
  неопределённой попытки в retryable-failure для целей каскада.
- **Вебхук мерчанту**: подписан HMAC, ретраи с backoff при не-2xx, идемпотентен на стороне
  мерчанта по (payment_id, status).
- **Смешанный приоритет (часть провайдеров с ручным priority, часть без)**: провайдеры с
  выставленным priority всегда идут первыми, в порядке priority; провайдеры без priority идут
  после них, среди себя — по adaptive score. Это соответствует правилу "ручной приоритет —
  закон": если он выставлен хоть у одного, он соблюдается для него, а не отменяет adaptive для
  остальных.
- **Вебхук/алерт при conflict**: конфликт (повторный success после уже завершённого каскада)
  не только пишется в `ReconciliationFlag`, но и уходит мерчанту отдельным типом события
  (`event: payment.conflict_detected`), отдельно от уже отправленного финального вебхука —
  чтобы конфликт не был "silent" (анти-цель), но при этом не переписывать/не повторно слать уже
  отправленный финальный статус.
- **Коррекция `ProviderStats` при позднем разрешении**: попытка в статусе `ambiguous`/
  `timed_out` сразу пишется в статистику как failure (чтобы adaptive-роутинг реагировал для
  следующих платежей без задержки); если позже приходит реальный исход и он отличается —
  статистика корректируется (декремент ошибочного счётчика, инкремент верного), а не остаётся
  навсегда искажённой.
- **Idempotency-Key с другим телом запроса**: тот же key с иным payload → `409 Conflict`,
  платёж не создаётся и не обрабатывается повторно с новыми данными.

## 5. Что остаётся на реализацию

- Точные Pydantic-схемы запросов/ответов.
- Точная SQLAlchemy-схема таблиц и индексов.
- Конкретные числа таймаутов/backoff/ретраев (разумные дефолты, через конфиг).
- pytest-покрытие корнер-кейсов: ambiguous→success-после-начатого-каскада (conflict),
  final-decline-не-каскадирует, retryable-decline-каскадирует, все-провайдеры-исчерпаны,
  повторный POST с тем же Idempotency-Key, повторный вебхук, adaptive-роутинг выбирает
  провайдера с большей историей успеха, manual-priority перекрывает adaptive.
- README: архитектурная схема (mermaid), запуск (`docker-compose up`), как прогнать каждый
  демо-сценарий, явные ограничения и что было бы сделано иначе с большим запасом времени.

## 6. Доработка по итогам ревью с CTO (2026-11-13)

Разбор этого проекта с CTO выявил, что ключевой anti-goal документа —
"молчаливое задвоение платежа без детекта" (раздел 2) — был заявлен решённым,
но реализован не до конца, плюс ряд предметных пробелов в платёжном домене
были не реализованы *и не названы* как известные ограничения. Зафиксированные
находки и то, что из них исправлено в этом цикле:

**Исправлено:**
- **Двойное списание было возможно по факту.** Если провайдер не подтверждал
  и не отклонял попытку за `reconciliation_deadline_seconds`, система считала
  это retryable-отказом и шла к следующему провайдеру — хотя реальный исход
  первой попытки был неизвестен, а не "скорее всего неудача". Это ровно тот
  механизм, которым можно задвоить списание. Исправлено: по истечении
  дедлайна без ответа каскад **останавливается полностью** (`payment.status =
  review_required`), следующий провайдер не вызывается, адаптивная статистика
  не трогается (раз исход неизвестен — не угадываем его для роутинга). Позже
  пришедший вебхук по этой попытке только логируется на `ProviderAttempt`
  (для тех.поддержки, чтобы свериться с провайдером) — `payment.status`
  автоматически не меняется никогда; ручное изменение статуса — отдельный
  инструмент/доступ к БД, не входит в API. Подробности и код —
  `app/cascade.py` (`mark_review_required`, ветка `review_required` в
  `handle_late_resolution`), сквозной разбор — `WEBHOOK_ASYNC_FLOW.md`,
  сценарии C/D.
- **Race condition на записи `Payment`.** `finalize_success`/`finalize_failed`/
  `handle_late_resolution` читали платёж (`session.refresh`), проверяли статус
  и писали — без защиты от того, что вторая сессия (вебхук от провайдера vs.
  фоновая задача каскада) делает то же самое в это же время. Исправлено через
  оптимистическую блокировку: `Payment.version` (SQLAlchemy `version_id_col`,
  `app/models.py`) — конкурентная запись по устаревшей версии кидает
  `StaleDataError` вместо тихой перезаписи; `cascade._retry_on_stale_payment`
  перехватывает её, перечитывает платёж и повторяет решение на свежих данных
  (до 3 попыток). Выбрана оптимистическая, а не `SELECT ... FOR UPDATE`,
  блокировка специально, чтобы одинаково работать и на Postgres (прод), и на
  SQLite (тесты) — `FOR UPDATE` на SQLite не рендерится.
- Побочный эффект первого фикса: правило "не каскадировать на неподтверждённый
  исход" применяется к `cascade.py` одинаково для `deposit` и `withdraw` —
  то есть закрывает двойное списание и для выплат, а не только для депозитов.

**Сознательно не реализовано в этом цикле — названо явно, не предполагается
по умолчанию** (детали и обоснование — README, раздел Limitations):
- Хранение/передача данных карты для второго PSP (vault, PCI DSS, network
  tokens) — `card_bin` есть, PAN/токена нет, по-настоящему каскадировать на
  реальных провайдерах без этого не получится.
- 3DS (каскад после challenge, liability shift, soft decline `1A`).
- Маппинг decline-кодов на реальные правила схем (Mastercard MAC, лимиты
  Visa на повторные попытки) — коды в проекте придуманы под моки.
- Разница в риск-профиле `withdraw` vs `deposit` за пределами уже описанного
  фикса (деньги, ушедшие клиенту, откатить сложнее, чем списание с карты).
- `card_bin`-роутинг, стоимость/комиссии провайдеров, circuit breaker,
  затухание `ProviderStats` по времени.
- Инструмент ручного разрешения `review_required`/`conflict` — статусы
  проставляются вручную (прямой доступ к БД), отдельного API/UI нет.
